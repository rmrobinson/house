## Bridges

[ ] group target support in the zigbee bridge, and likely an equivalent in the zwave bridge: let a policy or UI command target a whole set of lamps with ONE command instead of N per-device ones. zigbee2mqtt already has groups (published retained on `<base>/bridge/groups` with their members; the guest and primary bedrooms each have one, `guest_bedroom_lights` and `primary_bedroom_lights`) and takes commands on `<base>/<group>/set`, but bridges/zigbee ignores them - it only models `bridge/devices`. Why it is worth it (measured 2026-10-12 against the guest-bedroom group): a group command is one Zigbee multicast, so there is no per-bulb queue, retry or stale-route behaviour - 26 commands, ~0.3s each, both bulbs in lockstep within 10ms, no multi-second stalls - whereas the same bulbs commanded one at a time saw 2-19s delays, replayed or late commands landing after a newer one, and the bulbs ending up out of step. Open questions: (a) how a group appears to the house - most likely a Light device with its own id (e.g. zigbee-group-<id>) whose attributes are the intersection of its members' exposes (on/off always, brightness/colour only if every member has them), rather than a new device type; (b) confirmation - z2m publishes a group's state optimistically and there is no per-member acknowledgement, so a lost multicast frame leaves a member silently out of step; decide whether to read members back after a command (`/get`), and whether the group's own state should ever be trusted for toggles; (c) members are also devices, so the room aggregation in service/house/aggregation.go and the room views must not count a group on top of its members, and the group should probably have no room link of its own; (d) in-flight and burst behaviour - in a 4-step brightness burst sent 0.4s apart only 3 steps took effect (identically on both bulbs), so confirm how z2m coalesces back-to-back group steps and whether the CommandLane's supersede/coalesce rules should apply to a group target as they do to a device; (e) group membership is written into each bulb's own group table over the same radio path, so adding or removing a member can fail silently - surface membership drift rather than trusting z2m's record; (f) z2m `bridge/request/group/*` management (create, add/remove members) is out of scope here - groups are created in z2m and only consumed. Z-Wave: zwave-js can multicast to a node set (association groups / multicast, via zwave-js-ui) - investigate the same one-command-for-many shape there and share the selector design (a policy `home.send` step should be able to name a group id exactly as it names a device id). A hardware note from the same work: a bindable remote can control a group with no software in the path at all (switch2 is bound that way); a Green Power remote like the Hue Tap (switch1) cannot be bound and can only drive lights through policies, which is the main reason this item matters for the primary bedroom
